# ADR-0006 — Canonical operational-scope registry and assignment identity

**Status:** Accepted target architecture (2026-09-24); implementation and production data migration are NOT complete.  
**Supersedes:** [ADR-0005](0005-organization-operational-scope-integrity.md) **only where it requires a scope type + target ID in each assignment and defines GLOBAL as a no-ID assignment**. Its principles of owner authority, multi-scope responsibility, security, history and additive migration still apply.  
**Issue:** [#130](https://github.com/CHOUABBIA-AMINE/HidraAPI/issues/130).  
**Current-code baseline:** `main` at `678060ff4a43928be11cb242228a558353166b88`; repository `OrganizationId.newId()` generates UUID strings and topology `Pipeline.id` is `String`.

## Decision

### 1. One canonical scope identity

Introduce one organization-owned **registry** `OperationalScope` (a catalog of validated references, **not** a new owner of pipelines, facilities or equipment). Its database primary key `id BIGINT` is generated by PostgreSQL. Each registry record has an `OperationalScopeType` and an immutable typed **target reference**, e.g. `(PIPELINE, <topology pipeline ID>)`. A registry row is not an organization unit, topology asset or access permission.

Canonical responsibility association: `ResponsibilityAssignment.scopeId BIGINT NOT NULL` is an FK to `OperationalScope.id`. The assignment does **not** copy scope type, target ID, current code or current name. `OrganizationUnit` and `EmployeeAssignment` must not embed the four former operational scope fields after the verified migration and consumer cutover. One organizational unit may have zero-to-many independently effective-dated responsibility assignments; a scope may be assigned to multiple units and employees in distinct roles. No implicit inheritance of unit responsibilities by employees or child units.

Current display: responsibility → scope registry → scope type + target owner ID → owner **public read/resolver port** → authoritative current code/name/status. Registry must not accept independently writable, current code/name as identity; immutable provenance-labeled captured snapshots, if business-approved, are non-authoritative. If owner is unavailable, return an explicit unresolved status rather than fabricated or stale current details.

### 2. Scope registry invariants and keys

- Primary key is a positive generated `Long`, not an invented ID. `type` is mandatory.
- For `PIPELINE_SYSTEM, PIPELINE, FACILITY, EQUIPMENT, ORGANIZATION_UNIT`, `targetId` is nonblank and is **kept in the owning module's native canonical ID format** (currently topology `Pipeline.id` is `String`). Scope registration resolves the type/ID pair with the owning module, checks existence/assignability and approved lifecycle/authorization. A topology JPA repository is **not** a public cross-module resolver.
- For `GLOBAL`, use **exactly one registry row** `type = GLOBAL, targetId = NULL`. Its generated positive `id` is an ordinary `scopeId` on assignment; this is not a fabricated target-object ID. Permit global assignments only for explicitly approved responsibility roles and principals.
- `CUSTOM` is denied unless its owner namespace, resolver, lifecycle and permission policy are explicitly registered. Plain `CUSTOM` plus arbitrary targetId is insufficient; if used, add a validated namespace to its key.
- Unique identity for entity-backed scopes: `(type, targetId)` (plus namespace for registered CUSTOM). Use a separate partial unique index for GLOBAL singleton and a CHECK for GLOBAL-null vs entity-nonblank. Normalize/validate target IDs according to each owner's canonical scheme; never infer IDs from labels. Protect registration against concurrent duplicates with DB uniqueness plus idempotent lookup/retry.
- Database FK to registry guarantees existence of **registry row only**; cross-module target validity still requires owner validation, lifecycle events/reconciliation and documented TOCTOU handling. Never claim a polymorphic FK automatically validates underlying pipelines or facilities.
- Registry row deletion is restricted while referenced, and retirement/unassignable owner targets stop new assignments without deleting historical assignments.

### 3. Effective-dated responsibilities, authority and security

Keep `ResponsibilityAssignment` as the association owner; persist identity/assignee discriminator, `scopeId`, role, valid-from/to, status and audit metadata. Use half-open intervals `[validFrom, validTo)`, end optional; one active matching assignment for `(assigneeType, assigneeId, responsibilityType, scopeId)` per overlapping interval, while different roles/scopes can coexist. Define revoked/history semantics and an enforceable concurrent-write overlap strategy in its implementation task. Assignment is not an identity permission and does not authorize SCADA actuation. Separate owner authorization and audit checks apply.

### 4. Numeric ID request: separate conversion decision

Adopt `Long` **for the new registry PK and assignment FK only** in the initial scope correction. Do **not** silently convert existing UUID-string organization IDs or external topology IDs as part of this decision. Converting `OrganizationUnit.id`, `EmployeeAssignment.id`, and `ResponsibilityAssignment.id` to Long is a **separate, conditional migration**: inventory every referring column, foreign reference, Java model, ID factory, DTO, client, source-data crosswalk, historical record and deployment/backfill procedure; validate bidirectional old→new mapping and rollback before approval. Numeric organization IDs do not imply numeric topology target IDs. Changes across modules require their own owning roadmaps/ADRs if necessary.

### 5. Safe release order

1. Publish this ADR and amend organization roadmap; perform remaining `ORG-023` legacy-data/consumer/owner evidence work before destructive changes.
2. Introduce validated registry domain contract and owner-resolution/application ports without changing legacy writes.
3. Add an **additive** Flyway migration for registry, DB constraints and nullable transitional `scope_id` on responsibility; do not edit `V20260611_002__create_organization_tables.sql` and do not drop old fields or assume old scope ID is a registry ID.
4. Audit legacy tuples and map only verified `(type, targetId)` pairs to registry IDs. Quarantine ambiguities, orphans, mixed type/code/name, unregistered CUSTOM and GLOBAL with invented target IDs. Preserve responsibility history and employee/unit legacy scope intent for reviewed backfill.
5. Add validated assignment commands/queries, backfill verified associations, update read projections, APIs, JPA mappers and external consumers. Switch to mandatory `scope_id` and retire redundant fields only after confirmed reconciled cutover, tests, backup/recovery and approval.
6. Execute any String→Long conversion later under a separately reviewed ID-migration design; never cast UUID strings to BIGINT or rely on in-place PostgreSQL `ALTER TYPE` for that conversion.

No production schema or data changes are approved merely by accepting this ADR.

## Alternatives and tradeoffs

Persisting `(type, targetId)` directly on assignment (ADR-0005) was viable but duplicates type discrimination and owner-resolution logic on every assignment. A central registry enables an ordinary responsibility→registry FK and one canonical typed reference per target, at the cost of an extra table, registration flow, lifecycle management and owner-read dependency. Storing only the bare ID of a topology object without a registry was rejected because IDs are not guaranteed unique across owners/types.

## Verification requirements

- Two or more distinct pipeline/facility scopes can coexist for one organizational unit; one scope can be reused by multiple units.
- Persisted responsibility has exactly one valid registry FK and no independently writable type/code/name; lookup resolves type and current display correctly.
- Reject duplicate registry pair, unknown/ineligible target, unregistered CUSTOM, GLOBAL with targetId, improper role, overlapping same-role assignment; preserve roles and historic windows.
- Test concurrent registry registration, owner retirement/unavailability, reconciliation, authorization, database FK/CHECK/partial-unique constraints, additive Flyway migration, API consumer compatibility and rollback.
- Numeric ID change (if approved) separately validates every incoming/outgoing reference and source-data mapping, with no loss of legacy history.
