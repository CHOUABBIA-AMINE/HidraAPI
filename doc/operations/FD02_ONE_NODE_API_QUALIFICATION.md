# FD-02 — production-first single-node API smoke (HAPI-932)

## Status

CURRENT — HAPI-932 synthetic runtime qualification guidance; not a production deployment or operational acceptance.

**Scope:** Development-only synthetic qualification of one real Java 21 HidraAPI JAR and a single fresh PostgreSQL 16 database using production-profile configuration. This is neither a production deployment nor complete six-module business acceptance.

## Goal and decision rule

The smoke **fails** if the JAR cannot build and reach readiness, Flyway cannot migrate/validate the fresh schema, an ordinary non-superuser runtime principal cannot authenticate and execute a native Identity write/read, an unauthorized client gains protected data, the runtime account has DDL/protected-source read privileges, or the actual second JVM loses the first one's committed user ID. No step relaxes the repository's current authentication, authorization, audit or transaction rules.

Module-level acceptance remains with existing Full CI and native PostgreSQL test suites. FD-02 intentionally does not fabricate independent Workflow approvals or claim production IdP, company, asset, UI, HA, backup, SITE, industrial or release qualification.

## Repeatable isolated execution

Run in a disposable GitHub Actions hosted runner via **HidraAPI CI Qualification (isolated)**, `fd02-runtime` job. The job runs on the FD-02 file changes on `main` or by explicit `workflow_dispatch`. The PostgreSQL 16 service uses a throwaway migration/bootstrap credential derived from the isolated job identity (never a production secret). `scripts/qualification/fd02_one_node_runtime.sh` independently generates random runtime, application administrator and JWT credentials for that invocation. It creates a fresh `fd02_qualification` database owned by the isolated privileged PostgreSQL bootstrap administrator, applies the same packaged Flyway/PostgreSQL libraries to the unchanged source migrations, validates them, provisions a synthetic LOCAL provider and two active Audit reference catalog rows required by the native administrator bootstrap (`IDENTITY_LOCAL_ADMIN_BOOTSTRAP` as `EVENT_TYPE` and `SECURITY_ADMINISTRATION` as `EVENT_CATEGORY`), then starts a production-profile JAR with **only** the non-superuser runtime database identity. The migration authority is confined to the disposable CI database; the runner explicitly removes its password and related connection defaults from the child JVM environment, verifies that omission using the live process environment without printing values, and never passes the migration login to the application's datasource. It disables application Flyway auto-migration because migration/validation is handled by the **disposable CI-only privileged PostgreSQL bootstrap owner** (required by the existing Identity pgcrypto object invariant); Hibernate schema validation stays active.

The runtime's temporary privileges are limited to schema usage, table reads except explicit protected engineering/Identity-proof exclusions, Identity writes, and Audit event **INSERT** inherited from a distinct non-login `fd02_audit_append_writer` permission role. The Audit role cannot log in or be assumed with `SET ROLE`; it owns no objects and has no UPDATE, DELETE or TRUNCATE rights. The runner verifies this with actual PostgreSQL membership/ACL assertions and denied runtime mutations, then requires one real bootstrap-created Audit event. An attempted schema-owner UPDATE of that specific event must be rejected by the existing HMR-095 database trigger, independently of ordinary-user ACLs. They are **not** a production privilege specification. DDL and protected engineering reads must fail for the ordinary account. Access to the Identity commit-proof key and history relations is explicitly denied; those internal relations are not ordinary runtime data. The existing Identity migration validates trusted `pgcrypto` object ownership and must not be weakened to accommodate a disposable migration principal. The owner approved this additional **synthetic disposable** Audit insert permission for HAPI-932 only, not as a production grant matrix; further writers, roles or permissions remain separate configuration decisions. Do not bypass an existing negative authorization or immutable evidence trigger.

The initial JVM enables the controlled LOCAL administrator bootstrap and uses an explicit native HTTP issuer; the second JVM disables bootstrap, retains the database and signing key, and must return the same administrator and newly registered synthetic user IDs through genuine HTTP. No SQL fixture is used for the business registration; the only synthetic SQL references are the active LOCAL provider and two Audit catalog rows. The application itself must persist the administrator and its Audit event.

The independent client checks the actual `/api/v1/identity/authentication/login`, `/api/v1/identity/me` and `/api/v1/identity/users` routes, protected readback, missing/invalid bearer and invalid password denials. It also exercises available Organization, Party, Topology, Configuration and Workflow read/capability routes; these calls prove *route reachability*, not an end-to-end business process.

## Evidence and limitations

Read the job outcome and its attached `hidra-fd02-<sha>` artifact. Only after **the runtime job itself succeeds** may the single-node smoke be described as qualified at that exact SHA. `evidence.json` retains SHA, JAR digest, PostgreSQL major/minor version number, migration count, nonprivileged role checks, true JVM restart result and HTTP check totals. `initial.json` and `restart.json` include only route/status metadata and synthetic IDs. No credentials, JWTs, request bodies or protected errors are published. Evidence additionally records Audit catalog-family validation, INSERT-only permission-role membership, denied role switching/update/delete and the real bootstrap Audit record count; private runner build/migration/application logs are discarded on cleanup. The Python fixture tests and shell syntax checks alone **do not** constitute the runtime proof.

The test does not select TLS termination, secret manager, topology writer policy, production database permission matrix or any deployment target. Production release requires separate infrastructure and operations authorization.
